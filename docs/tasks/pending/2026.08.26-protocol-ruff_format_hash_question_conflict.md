# Task: Resolve `ruff format` ↔ `#?` comment convention conflict

## 1. Goal
The repo mandates the `#?` comment prefix (no space) for IDE-syntax-friendly
explanatory comments (per the python-packaging skill + AGENTS.md §7 of the
shared python guide). However `ruff format --check` fails on 22+ files
because ruff's default behaviour rewrites `#?` → `# ?`.

Today AGENTS.md §2.6 instructs "run `ruff format --check` before commits"
but that command *cannot pass* without giving up the `#?` convention or
suppressing ruff's comment rewrite.

This task makes the project decision explicit and removes the contradiction.

## 2. Scope
### In Scope
- Document the chosen resolution in AGENTS.md §2.6 with a one-line note
  explaining why.
- Configure ruff (in `pyproject.toml`) to match the decision (see §3).
- Verify the entire `src/` + `tests/` tree passes the chosen CI gate.

### Out of Scope
- Replacing `#?` with `# ?` everywhere (that would be a separate
  project-wide reformat task).
- Adding a CI job for `ruff format --check` — that is
  `2026.08.26-protocol-ci_ruff_format_gate.md` and depends on this task.

## 3. Approach
The two viable options:

**Option A (recommended): keep `#?`, exclude comment reformat from ruff.**
- Add `[tool.ruff.format] exclude = ["#?", ...]` style isn't a real ruff
  flag. Real option: use `ruff format --check --no-respect-gitignore` and
  disable the comment-spacing rule via `[tool.ruff.format]` config. Ruff
  does not currently expose a "skip leading character rewrite" knob.
- The pragmatic move: accept that `ruff format` reformats comments, and
  have CI run `ruff format --check` only against a fresh checkout of
  generated/third-party code (none in this repo) — OR run `ruff check`
  only and drop `ruff format` from the canonical workflow.
- Since this repo has 0% acceptance of `# ?` style (every explanatory
  comment uses `#?`), the cleanest decision is to **drop `ruff format`
  from the canonical workflow entirely** and rely on ruff's *check* (lint
  + import sort + bugbear) plus `mypy` for code style enforcement.

**Option B (rejected): migrate all `#?` → `# ?`.**
- Touches every explanatory comment in the codebase. The skill guide
  *explicitly* recommends `#?` for IDE syntax highlighting. Risk of
  drift and slow review.

**Decision: Option A.** Update AGENTS.md §2.6 to drop `ruff format`
from the canonical pre-commit workflow. Ruff *check* (lint, isort,
bugbear) remains the source of code-style truth. CI runs `ruff check`
only.

## 4. Implementation Plan
1. **`AGENTS.md`**: in §2.6 ("Linting / Formatting"), replace
   "Run `ruff check .` and `ruff format --check .` before commits."
   with two lines that explain the decision:
   - "Run `ruff check .` before commits (lint + import sort + bugbear)."
   - "Note: `ruff format` is intentionally NOT in the canonical workflow
     because ruff rewrites our mandated `#?` explanatory comments to
     `# ?`. The `#?` convention is required by the python-packaging
     skill for IDE syntax highlighting. See
     `docs/tasks/done/2026.08.26-protocol-ruff_format_hash_question_conflict.md`
     for the rationale."
2. **`pyproject.toml`**: no change required (we are keeping the existing
   `[tool.ruff.format]` block in place; it just stops being run).
3. **Optional cleanup**: add a one-line `[tool.ruff.lint] # noqa`
   or comment near the `[tool.ruff.format]` block documenting why it's
   kept but unused. Skip unless the maintainer asks.

## 6. Notes
- This decision is reversible if the project later decides to migrate
  to `# ?`. The only artefact that needs to change is AGENTS.md §2.6
  + adding a `ruff format --check` CI job.
- Future `format` work (e.g. if someone wants `ruff format` for
  unrelated whitespace rules) would need to either (a) reformat `#?`
  to `# ?` globally first, or (b) add `ruff format` to a `pre-commit`
  hook that runs *before* comment writes happen — neither is in scope.
